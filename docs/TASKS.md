# Tasks

The backlog for the hackathon. One task = one owner = one branch = one PR.

This file is the **spec** and the **owner list**. Owners are assigned by Alberto and Claude; the live **status** lives in GitHub Issues (one issue per task, same ID in the title). Do not edit this file to claim or move work. If you think an assignment is wrong, tell Alberto.

How to work on a task:

1. Read [`PRODUCT.md`](PRODUCT.md) and [`ARCHITECTURE.md`](ARCHITECTURE.md) first.
2. Open your issue, create the branch (`feat/t5-companion`), stay inside the **Folders** column.
3. Open the PR with `Closes #<issue>`. Alberto reviews and merges.
4. If your dependency is not merged yet, build against the types in `src/types/` and a local mock. **Do not wait.**

The old restroom map and menu reader tasks (the previous T1 to T12) are void. Their code is kept but paused.

## Task details

Each task is done when its **Done when** list is true, `pnpm check` passes and the PR template is filled.

### T1 · Local data store and state hook (Juan)

Build the persistence layer described in `ARCHITECTURE.md` section 5.

- `src/lib/storage/`: `createEmptyState()`, `loadState()`, `saveState()`, `migrate()`, `exportBackup()`, `importBackup()`. `zod` schemas that match `src/types/` exactly. Corrupt data falls back to an empty state and keeps the raw value under a backup key.
- `src/hooks/useAppState.ts` and `src/components/providers/AppStateProvider/` (one new line in `AppProviders` is approved).
- `addCheckIn` replaces an existing check-in of the same day. After `addCheckIn` and `addMissionLog`, call `syncCompanion` from `src/lib/rewards` (T3) so rewards are derived from the logs.
- Typed actions: `addCheckIn`, `addMissionLog`, `saveParentLog`, `addFoodEntry`, `addConsultation`, `equipItem`, `setSettings`, `setChild`, `loadDemo`, `clearAll`.
- Unlock state of parent mode is **not** here (memory only, owned by T10).
- The context exposes `isReady`: it is `false` until the stored state is loaded after mount. Screens must wait for `isReady` before redirecting (for example to `/parent/setup`), so the server and the first client render match.

**Done when:** unit tests cover load, save, migrate, corrupt data, backup round trip; the hook works in a test with Testing Library; the app does not crash with empty storage or with garbage in storage.

### T2 · Demo data generator (Alberto)

- `buildDemoState()` returns a complete `AppState` with `isDemo: true`: about 90 days, two consultations, one flare and its recovery, plausible sleep and school, a few food entries on discomfort days, mission logs with the three companies, a partly filled companion. Seeded and deterministic. No drug names, no real data.

**Done when:** tests check that the state validates against the T1 schemas (once merged), is deterministic, and contains at least one flare arc and two consultations.

### T3 · Rewards and PIN logic (Alberto)

**Done when:** a test proves the reward never depends on the answer values or the mission kind; a test proves progress never decreases; PIN tests cover correct, wrong, lock and reset.

- Use the ids in `src/config/content-ids.ts` for the three core questions and the missions. If you change or add one, update that file in the same PR and tell Alberto, because the demo data and the screens use it.
- Read `PRODUCT.md` section 5.4 and 6 before writing a word. If a statement needs a source and has none, write `// source: to verify`.

### W1 · Watch data via Google Health API (Álvaro)

Issue #85. Decided by Alberto on 2026-10-04 (`docs/DECISIONS.md`). Product rules: `PRODUCT.md` section 5.6. Data flow: `ARCHITECTURE.md` section 8c. A test with an Amazfit GTS 2 proved the path (Zepp, Health Connect, Google Health app, Google Health API v4) and returned steps, heart rate and sleep stages.

- **Folders:** `src/lib/wearables/` (pure logic and tests), a parent-mode watch card (`src/components/features/parent-mode/WatchCard/`), a watch section in the doctor report (`src/components/features/doctor-report/` and `src/lib/report/`, coordinate with Juan), and `src/app/api/watch/` **only if needed**. Shared files (`src/types`, `src/config/app.ts` routes, `package.json`) need Alberto's OK: ask first.
- **Your call:** option A (the parent phone reads the API directly and keeps the data on the device) or option B (a server pipeline stores it). Write the choice and why in the PR. Option B must follow the privacy guardrails in `PRODUCT.md` section 5.6 (EU region, pseudonymous ids, service-role access only, no analytics, deletable on request) and sends only watch data.
- Read-only scopes only: `googlehealth.activity_and_fitness`, `googlehealth.health_metrics_and_measurements`, `googlehealth.sleep`. Google Fit is not used. The parent connects their Google account and consents; the card says what is read and offers Disconnect.
- Map responses to `WatchDay` (validated with `zod`), aggregated per local calendar day with `src/lib/dates`. Summaries are descriptive: totals, averages, ranges.
- Label everything "From the watch (Google Health)". Days without data show "No watch data yet". Never fill or guess.
- **Not allowed:** risk scores, alerts, predictions, clinical thresholds, "detects flares" claims, step goals or streaks, any reward that depends on watch data, showing heart rate or sleep to the child, secrets in the repo, issues or client code, and sending check-ins, parent log or food diary to a server.
- Add the new env var names to `.env.example`. Demo data may include watch days only if they are labelled "Demo data".

**Done when:** a parent can connect, see the watch card with a few days of data, the doctor report shows the watch section, a day with no data says "No watch data yet", disconnecting works, `src/lib/wearables/` is tested, and `pnpm check` passes.
